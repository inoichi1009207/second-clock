# 竞品分析 · 第二时钟

> **这份分析的目的是证伪，不是背书。** 三个自称的差异点逐个拿去找先例，找到了就如实写。
>
> 结论先说：**「首创开封后计时」这个说法站不住**——有产品做了，只是要么让用户自己填天数、
> 要么只覆盖极窄的药种。站得住的是**覆盖广度 × 拒绝猜测的机制**这个组合。
>
> **方法**：两条独立检索链路交叉执行——(A) Bing／搜狗／DuckDuckGo 三引擎 54 组查询 +
> App Store 页面原文抓取；(B) Codex CLI 独立联网调研，24 个条目 / 29 个来源链接。
> 两边结论一致处直接采信，**不一致处以更保守的一方为准**（第三条差异点即如此）。
> 判据是检索到的原文，不采信任何模型的记忆。检索时间 2026-08-09。
> 完整原始记录见 `clipboard/competitor-scan.md`。

## 一、结论

| 自称的差异点 | 裁定 | 一句话依据 |
|---|---|---|
| ① 内置「开封后有效期」数据库 | **概念已有先例，规模未找到对手** | 同类要么给空字段让用户填（Pharma Stock、安心药箱），要么只覆盖窄药种（GLP-1、眼药水、胰岛素）；未找到覆盖约 1832 条中文家庭药品/用品且离线可查的产品 |
| ② 多厂商模型独立交叉验证 | **未找到先例** | 消费级健康视觉 AI（SkinVision、Aysa）公开表述均为单一算法/模型；该技术在开发与事实核查领域有讨论，用于消费级用药安全未检索到先例 |
| ③ 同名多剂型不猜、交还用户指认 | **通用 UX 原则已有，此具体规则未找到先例** | 未找到另一产品实现「同一商品名命中多剂型 → 发现期限不同 → 拒绝自动选中 → 就地要求照药盒指认」 |

**品类判断**：**不是新品类，是两个成熟品类之间的空隙**。
一边是**服药提醒**（Medisafe、MyTherapy、Pill Reminder、Apple 健康·用药——解决"该吃药了"）；
另一边是**药师用的 BUD 计算器**（USP 795/797 标准下算调配制剂失效期，专业工具、不带家庭药品库）。
中间还有一层**只管包装印刷效期**的家庭药箱 app（智药箱、i药管家、家庭药盒管家、MyAidKit、ExpirAlert）。
「家里这盒**开过封**的药还能用到哪天」这个问题，三边都不完整地接。

### C 类 · 服药提醒（另一个品类）

Medisafe、MyTherapy、Pill Reminder、Apple 健康·用药、以及国内九款横评里的叮咛吃药提醒/吃药提醒管家/服药精灵/药准时等——
**全部未找到处理开封后效期**。MyTherapy 的 supply 功能是防止药吃完，不是防失效。
用药助手（丁香园）是临床查药工具，不做家庭库存。

### D 类 · 药师用的 BUD 工具（邻近但非同类）

BUD Calculator（bud.etreacy.me）、EZ Virtual Tools BUD Calculator（USP 795/797）、RxTools BUD Calc、MedExpiry。
**从配制日算起**，面向调配与分装，要求使用者先选制剂类别与储存条件；无家庭药品库、无提醒。

### E 类 · 消费级健康视觉 AI（用于对照差异点②）

SkinVision（官方表述 "the algorithm"）、Aysa（Google Play 表述为 a machine-learning model，模糊照片可拒绝分析）。
**两者都是单一模型**，未见双厂商独立比对与分歧拒答。

## 三、三个差异点逐项裁定

### ① 内置开封后效期数据库 —— 概念已有先例，规模未找到对手

**被证伪的部分**：不能说「第一个想到开封后计时」。Pharma Stock 有 "Shelf Life After Opening"、
安心药箱有「开封后使用期限」、EyeDrop 专做眼药水开封提醒、Regimen 的计算器对 GLP-1 类**直接给 discard date**。

**仍然成立的部分**：这些要么是**空字段**（用户得自己知道天数，而那正是原始难题），
要么**只覆盖极窄的药种**（几种减重针、眼药水、胰岛素）。
检索未找到另一款覆盖约 1832 条中文家庭药品与医疗用品、带剂型兜底规则、且离线可查的消费产品。
已知最大的同类离线库是安心药箱的 **57 款**。

> **准确的说法**：不是「只有我做了开封效期」，而是
> **「别人给你一个填天数的格子，或者只覆盖几种药；我把一个家庭药箱能装下的东西都填好了」**。

### ② 多厂商模型独立交叉验证 —— 未找到先例

「多 AI 交叉验证」作为技术手段已有讨论（阿里云/腾讯云开发者社区关于 GPT-4/Claude/Gemini 共识度的文章、
GitHub 上的 Dual-LLM `consensus` 框架），**所以技术本身不是原创**。

但用在**消费级用药安全**上未检索到先例。最接近的对照是 SkinVision 与 Aysa——同为拍照的消费级健康 AI，
公开表述均为单一算法；Aysa 会对模糊照片拒绝分析，那是**单模型自查**，不是两家独立比对。
安心药箱的「未识别到明确有效期时保持『有效期待核对』」同理：同一条 fail-closed 原则，单模型实现。

### ③ 同名多剂型不猜 —— 通用原则已有，此具体规则未找到先例

「置信度不足就要求人工确认」是成熟的 UX 原则，眼药水专用产品则靠限定剂型直接回避了歧义。
但未找到另一个产品明确实现这条链路：**同一中文商品名命中多个剂型 → 发现这些剂型的开封期限不同 →
拒绝自动选中 → 就地要求用户对照药盒指认**。

两条独立检索链路在这一条上给出了不同标签（一方「未找到先例」，一方「部分存在」），
**本文按更保守的一方表述**。

## 四、最难反驳的一点（两条，都如实列出）

**其一：数量不等于壁垒。**
如果拿不出数据来源、每条规则的可追溯性、更新机制与真实识别错误率，
**1832 就只是「一张更大的日期表」**。这一点是成立的批评——本作品的 1832 条里
相当一部分是剂型通用参考值而非逐条核到说明书原文，产品内与文档中均已标注「参考值」。
**数据量的领先不等于数据精度的领先。**

**其二：最终输出仍然只是一个日期。**
Pharma Stock 已经把开封后保质期、药盒扫描、库存与通知放进同一个应用。
从产品形态上看，差距不在"有没有这个功能"，而在"拿不准的时候它做什么"。

**能站住的回应**：日期计算器不会拒绝回答。本作品最花力气的三处——
两家 AI 不一致就不代填、同名多剂型交还用户指认、识别出的有效期一律只作待确认——
**都是在减少它给出的答案数量**。它交付的不是 `开封日 + N 天`，
而是**在无法可靠确定 N 时，不制造一个看起来很精确的错误日期**。

## 五、可直接引用的表述

**40 字版（用于参赛描述）**：

> 服药提醒 app 管「该吃药了」，药师的 BUD 计算器管调配失效期，**家里这盒开过封的药还能用到哪天，中间没人接**。

**一句话版（用于问答）**：

> 同类要么给你一个「开封后可用天数」的空格子让你自己填——而"填多少"正是原始难题；
> 要么只覆盖几种减重针或眼药水。本作品把一个家庭药箱装得下的 1832 条都填好了，
> 并在拿不准时明确拒绝替你猜。

**面对「这不就是个带数据库的日期计算器」**：

> 日期计算器不会拒绝回答。这个作品最花力气的三处都是在**减少**它给出的答案数量。
> 难点从来不是日期加法，是**给哪盒药套哪条期限**。

## 六、商业化前景（诚实评估）

### 结论：C 端直接变现基本没戏，价值在 B 端

三条硬约束叠在一起，决定了 C 端订阅或广告都撑不住：

| 约束 | 后果 |
|---|---|
| **极低频** | 加一盒药，然后几周不打开。DAU 撑不起广告，也撑不起订阅的续费理由 |
| **医疗合规** | 国内提供药品信息服务需《互联网药品信息服务资格证书》；获客还没开始，合规成本先来 |
| **付费意愿** | 用户不会为"提醒我扔药"付月费。这是**避免损失**类需求，感知价值远低于**获得收益**类 |

C 端若一定要做，**买断制优于订阅**（低频工具的经典解法），但天花板很低，
更适合当作获客与信任建立的入口，不当作收入来源。

### 真正可卖的是「数据 + 判定机制」，卖给已有流量与资质的一方

| 方向 | 买家 | 为什么他们会买 |
|---|---|---|
| **医药电商售后增值** | 阿里健康、美团买药、叮当快药等 | "开封后还能用多久"是客服高频问题。接进商品页/订单售后可降低咨询量与退换货纠纷，属现成流量上的低成本增值 |
| **机构效期管理**（最明确） | 医院科室、连锁药房、养老机构 | `效期管家` 已证明该市场付费意愿明确（急救药品效期关联检查与考核）。**差异化正是补上"开封后"那一段**——开封的胰岛素、配好的抗生素混悬液、开瓶的消毒液，是护理场景的真实痛点，而现有产品只管印刷效期 |
| **数据授权 / API 计费** | 智能药盒与家用医疗器械厂商、健康管理与保险的服务模块 | 他们要的是一个能嵌进自己产品的查询能力，不想自建药学数据 |

### 与"数据量不是壁垒"的关系

数据会被追平——这一点在第四节已经承认。但 **B 端买的从来不是数据本身**，
是「**可追溯来源 + 拿不准时拒绝作答 + 出错时责任边界清楚**」这一整套。
对他们这是合规刚需，不是锦上添花：一个会在不确定时硬给答案的数据源，
他们**不敢接**，因为责任会落到他们头上。

### 要走 B 端，现在最大的技术债会立刻变成阻碍

1832 条里相当一部分是**剂型通用参考值，不是逐条核到说明书原文**。
C 端标一句"参考值"可以过去；B 端客户会要求**每条可追溯到出处、并有更新机制**。

因此 B 端化的第一步不是销售，是**把数据来源逐条落账**：
每条给出依据（说明书 / 药典通则 / 行业标准）、核验日期、责任人，并建立随说明书变更的更新流程。
这件事的工作量远大于把条目数从 1832 堆到 5000，**但它才是真正形成壁垒的那部分**。

### 不建议的方向

- **卖广告位给药企**：触及药品广告监管，且与作品"只做时间提醒、不做用药建议"的定位直接冲突
- **做成用药提醒 App**：那是 Medisafe / MyTherapy 的成熟战场，正面竞争没有胜算，也丢掉了自己的差异点
- **靠数据量竞争**：见第四节，这条路会被下一代模型迅速抹平
